Civic Pulse: technical guide for junior developers

Audience: a developer joining this codebase. Describes the current implementation; recheck the manifests and release evidence as the application evolves.

This guide explains the implemented code, not just the intended architecture. Read the PRD, design system, architecture, database contract and API contract for authoritative requirements. The application is not approved for production launch; see the launch audit.

Companion: illustrated end-user guide. Printable/offline version: technical guide HTML. Open the HTML in a browser and use Print / Save as PDF.

1. What the application does

Civic Pulse serves one Resident Welfare Association (RWA). Residents (voter role) sign in with an emailed six-digit code and submit once for their frozen household entitlement. RWA Admins (rwa-admin) manage the register and votes; RWA ReadOnly committee observers (rwa-readonly) inspect authorized management data but cannot change it.

  • PUBLIC poll: configured single-select or multi-select; one ballot and participation per household. Authorized completed results contain representative names, household identifiers and the final selected option set.
  • PRIVATE election: one candidate or NOTA (None of the Above) for every office. Storage and results use aggregate counters, not retrievable individual ballots. NOTA is counted separately and never wins; the highest-count candidate is elected even if NOTA receives more votes.
  • Lifecycle: Draft, Scheduled, Active, Completed or Cancelled. Type and status are different concepts.
  • Results: private to entitled Residents and authorized RWA Admin/ReadOnly personas; CSV is required and PDF is implemented but can be disabled.
  • Operations: audit history, bounded retention, encrypted backups/restore, health checks and maintenance mode.

Application-level PRIVATE privacy is not cryptographic anonymity. Privileged infrastructure operators, WAL/backups and very small electorates can allow inference. Never describe the system as secret from all operators.

Term Meaning

3. First hour in the repository

  1. Follow LOCAL_SETUP.md for the complete Windows setup and isolated Supabase test project. Never use production for development.
  2. Inspect package.json, .nvmrc, .env.example, and AGENTS.md.
  3. Put Node 24 on PATH. Use npm ci with the committed lockfile for a fresh checkout. The existing local guide also describes portable tools/corporate CA setup.
  4. Supply your own ignored local environment configuration. Do not copy an actual developer's secrets or publish them in issues, screenshots or commits.
  5. Start with npm run dev. Open the address reported by Next.js; ordinary local development uses port 3000.
  6. Sign in with a deliberately provisioned test account. New installations require migrations, settings and a controlled first administrator; visiting the site does not create an admin.
  7. Run npm test, npm run typecheck and npm run lint.
  8. Trace one feature using section 5 before attempting changes.

Never disable certificate verification to solve corporate TLS problems. Configure the approved CA for the relevant tooling. Existing live-test helpers have a documented TLS-verification weakness; do not copy that pattern into new runtime/deployment code.

5. Trace a real feature: submit a ballot

Read these files in order:

  1. Vote page obtains a guarded page context and authorized vote detail.
  2. BallotForm renders choices and keeps unsent selections in component/page memory.
  3. Browser API helper sends a same-origin JSON request with a CSRF token and validates the response envelope.
  4. Submission route checks Origin/CSRF, validates the ID/body and obtains an enabled member context.
  5. Submission service enforces a profile budget and calls cast_vote using the member's own client.
  6. cast_vote migration locks/rechecks/validates/writes atomically; the PUBLIC multi-select migration adds selection-set replacement and dispatches single- versus multi-select submissions; the NOTA migration names the built-in PRIVATE choice and changes its result projection; the live PRIVATE turnout migration returns turnout without exposing office totals while the election is active.
  7. Identifier label migration added the first RWA-wide display label; the household label migration replaces it with a household label and a Number/ID identifier kind returned by the profile, branding and public identity routines. The PUBLIC/PRIVATE migration renames the stored voting types.
  8. RWA profile migration adds guarded profile settings with RWA Admin/ReadOnly reads and Admin-only updates, and the branding migration adds the accent palette, welcome message, the member branding projection and the service-role-only public identity routine. The optional contact migration lets administrators leave the address, email and phone blank so they are hidden.
  9. After commit the response is participation-only: voteId and submitted: true, wrapped in the common envelope.
  10. A lost, malformed or unavailable acknowledgement triggers an own-participation check. The client must not blindly repeat a submission. 
Browser POST /api/votes/{id}/submission
  -> exact Origin + CSRF
  -> verified Auth identity + current enabled profile
  -> Zod/body/UUID validation and shared rate limit
  -> user-session RPC cast_vote
       -> lock vote, recheck entitlement/status/deadline
       -> insert unique participation
       -> PUBLIC: insert or replace the selected response set
          PRIVATE: increment one counter per office
       -> whole transaction commits, or all changes roll back
  -> safe acknowledgement (no PRIVATE selections)

The definitive deadline check uses the database clock after locking, not the browser clock, request arrival time or transaction-start time. A request waiting for a lock until the deadline is rejected. A transaction admitted before the deadline can commit afterward.

6. Authentication, sessions and authorization

Sign-in flow

  1. A controlled administrator provisions the email identity/profile, or the resident self-registers at /register. Supabase Auth public signup stays disabled: self-registration uses the server's privileged Auth client, then the service-role routine self_register_resident creates a suspended profile (self_registered = true) and an ineligible household in one audited transaction. It checks the email first (any existing profile, DUPLICATE_EMAIL), then membership in the configured Default Households when any exist (UNKNOWN_HOUSEHOLD, also pre-checked before the Auth stage), then the normalized household (DUPLICATE_IDENTIFIER); budgets are per email, per household and global, with a honeypot field. An administrator must still enable the account and make the household eligible.
  2. The code-request route normalizes/validates the email and returns generic guidance. It must not reveal whether an address is registered.
  3. Supabase handles six-digit, expiring, single-use email codes. Production requires custom SMTP; test helpers can obtain codes through supported Auth administration without email.
  4. Verification requires both a valid Auth session and a current enabled application profile.
  5. The server-side SDK writes session cookies. Shared cookie hardening applies HttpOnly, Secure in production, SameSite=Lax and a provisional 14-day sliding browser lifetime.
  6. Proxy session refresh refreshes before Server Component rendering and forwards new cookies to both browser and request. Server Components cannot themselves write cookies.
  7. Protected APIs use getUser and current profile checks. Role comes from the database profile, not user-editable JWT metadata.
  8. Sign out uses supported Auth behavior. Current application suspension/role checks remain essential because issued tokens are not universally revoked instantly.

CSRF context is a separate HttpOnly cookie; production uses a host-only Secure cookie and SameSite=Strict. The page exposes a derived token, not that secret context. Do not confuse CSRF and session cookies.

The role flags are exclusive, only an administrator changes roles, and a household is optional for both management roles — an enabled rwa-admin or rwa-readonly without one reads its authorized scope but has no ballot, while an ordinary resident needs a household before enablement. Neither management role grants another household's ballot entitlement.

Suspended/deleted/unprovisioned identities do not gain access merely by holding a valid token. Management pages use a plain not-found for accounts without administrative read capability; mutation APIs require the current RWA Admin role. Inaccessible vote IDs are indistinguishable from nonexistent ones.

7. Database model and invariants

For the full column/key/cardinality diagram, see the detailed Mermaid ERD in the database contract. It shows Supabase Auth as an external identity and distinguishes PUBLIC response rows from PRIVATE aggregate counters.

Residents are reviewed in one table with their RLS-authorized flat assignment and eligibility. The page defaults to the implicit voter role; selecting All Roles is explicit.

The register UI routes live only under /admin/residents. Former Accounts and Households UI routes are removed and return 404, without redirects; navigation, browser tests and screenshot workflows use Residents directly. listResidentTable calls the enabled-committee-only get_resident_table_page RPC from migration 20261115100000_resident_table_controls. It returns only the bounded ordered IDs and exact page/count metadata from one statement snapshot. Allowlisted sorting and all filters run before pagination; the service validates metadata and enriches only those IDs with profiles, households and supported Auth identities, including current App Support flags. The older listResidents cursor service remains compatible. Concurrent edits may move rows between requests. Account API paths, filters and profile-ID ordering and optional-household provisioning remain compatible; the stricter voter requirement is in the admin form. Settings supplies allowed flat identifiers, not assignments. Apply the new read-only routine before deploying this table revision; the app does not migrate at startup. No voting permission is introduced. Selections are current-page only and clear on sort/filter/page/size changes. The two actions reuse the existing per-account/per-household PATCH endpoints, not a bulk database write or new grant. Access and eligibility remain independent; admins without flats can be enabled only through explicit inclusion and a warning. Deleted/missing-assignment/already-satisfied rows are excluded as appropriate. Every request rechecks permissions and commits separately. Uncertain failures stop the batch; UI completion never rolls back earlier records or conceals an unknown outcome. Existing mutation/provider limits apply; the actions need no new write routine.

The table controls replace the separate Residents filter form with sortable/filterable column headings, including the icon-only Source column immediately before Actions, and all controls in Sort & Filter on phones. Source has no separate top filter; its ascending order is Admin-registered then Self-registered, reversed for descending. Migration 20261117100000_resident_source_sort.sql adds the global source sort key without changing the existing boolean source filter or API contracts. Representative and identifier use literal case-insensitive substring matching; names do not search Auth email. The page maps URL identifier to RPC identifierContains after migration 20261116100000; the old exact RPC filter and cursor APIs remain compatible. Settings identifier suggestions accept partial text via explicit allowCustomValue on the shared combobox; onboarding keeps its strict default. Last Changed uses profile timestamps and inclusive/exclusive instant bounds entered in the browser zone. Top-layer native popovers avoid table clipping; their dropdown lists expand in flow within the scrollable panel. Observers retain these controls outside management-disabled fields. The Clear filters link removes active filter parameters and returns to page 1 while preserving the current sort, direction and page size.

CSV import checks every record without overwriting existing state, then applies ready rows independently. Exact retries are skipped; conflicting identifiers, names, roles, assignments or eligibility are reported. Auth provisioning and database writes are not one transaction. Newly provisioned profiles remain suspended; administrators use the existing confirmed account workflow to enable them after review. Unknown/partial failures stop subsequent rows and require a recheck, not blind account deletion. CSV records remain in page memory only.

Scheduling uses the same guarded freeze helper as immediate activation. opens_at is the effective start and scheduled_at is the confirmation/freeze time; activated_at stores the effective start even while scheduled. Ballot, electorate and representative snapshots freeze now, not at opening. RLS and the member projection hide candidates/options before opening. Database-time reconciliation under the vote lock opens due votes, and a missed whole window completes at the original deadline. Strictly before opening, a confirmed reasoned withdrawal clears snapshots and zero counters, advances the revision, and requires new preview. It never reopens an active or terminal vote. See the architecture implementation map and API/schema sections for exact paths/contracts.

Critical constraints:

  • Unique participation and whole-transaction rollback prevent duplicate/partial ballots.
  • Frozen content and representatives cannot be edited after activation; an active deadline moves only through the audited deadline change.
  • Candidate IDs must belong to the submitted office/vote.
  • For each completed PRIVATE office, candidate counts plus NOTA equal submitted ballots.
  • Every PUBLIC participation has at least one selected option and obeys its configured cap. Multi-select option counts can exceed participation. Invariant failure withholds results rather than fabricating a fix.
  • Terminal votes cannot reopen. Accepted submissions cannot be edited, deleted manually or withdrawn.
  • Counts/audit bigints use decimal strings across API boundaries to avoid unsafe JavaScript coercion.
  • Current suspension blocks access without erasing accepted participation or changing the frozen turnout denominator.

Permissions

All application tables have RLS and restricted grants. Ordinary users/admins cannot directly read choice tables or write application tables. Guarded functions independently check identity and capability. Restricted non-login owners have fixed search paths; private data is not published to Realtime.

The privileged client bypasses RLS: use it only in the established provisioning/Auth administration, limiter and narrowly scoped reconciliation paths. Do not use it for ordinary ballot/result access.

8. Lifecycle and register workflows

Drafts can be incomplete. Every edit increments draftRevision; an update includes the expected revision. A stale edit receives a conflict rather than overwriting someone else's work. Preview identifies its version, and activation must confirm that same version.

Activation checks ballot validity, current selected representatives, future deadline, approvals and retention configuration. It freezes the electorate, historical identity/display data and ballot. Editing a household later affects future votes only. While the vote is Active an administrator may move only its deadline (later or earlier, at least 5 minutes ahead, with an audited reason) through change_vote_deadline.

Supabase Cron completes due votes and runs bounded retention. The scheduling role has narrow function grants. Scheduled completion records the deadline as effective completion time even if processing is late. Authorized reads may reconcile an overdue vote, but the transactional deadline remains authoritative.

Register changes span Auth and application records; they are not one distributed transaction:

  • Create a profile suspended; ordinary residents need a household before enabling.
  • Email changes preflight identity ownership, block access and verify Auth consistency before restoring prior access.
  • Provider failures surface partial-workflow errors. Do not silently enable an inconsistent account.
  • Repeated suspension/deletion status can retry an incomplete Auth ban. A deleted profile is not restored or edited.
  • At least one enabled administrator must remain.

10. Results, exports and UI conventions

The database result projection is validated and transformed in shared result contracts. Screen, CSV and PDF derive from it, not separate counting implementations.

  • Frozen eligible households are the turnout denominator.
  • Per-office percent uses submitted ballots and eligiblePercent uses eligible households (shown in the bars); zero denominators are not applicable.
  • Zero ballots or zero candidate votes have no winner. Positive tied candidate leaders remain ties. NOTA is not a candidate and cannot win.
  • Verify the NOTA winner rule against bylaws, along with the early-completion rule, before real voting.
  • PUBLIC names/households are frozen snapshots, with no email in exports.
  • PRIVATE exports contain aggregate data only.
  • Rendering completes before success headers. A render error returns a clean failure, not a partially successful document.
  • Current process-local render slots: eight CSV, two PDF, bounded wait. These are not a global cross-instance queue.
  • PDF fonts are bundled and traced for deployment; unsupported text is explicitly refused, with CSV guidance.

Use UI primitives for status, validation, focus, dialogs and accessible fields. Preserve 48px touch targets, 16px input text, semantic tokens, visible focus and native radios. A button's disabled state is not authorization. The shared content token in global styles has no maximum width: pages, headers and footers fill the viewport minus 16px phone or 24px desktop gutters. Form/ballot and short-copy blocks retain their independent 640px bounds; table regions contain any horizontal overflow. Shared page-header descriptions are an exception to the short-copy limit: they fill the available space beside actions and wrap responsively. Form-focused route wrappers center the title/description/form controls at 640px, not each field individually: resident new/detail/eligibility/import, Settings, vote new/detail/preview and the voter ballot. Access/register/contact/privacy were already centered. data-form-page marks the adjusted wrappers for browser regressions. Directory, audit, participation and results keep their wider workspaces; after Check Register, import preview/results use a separate full-content-width shared table, with stacked label/value rows on phones. Global breadcrumbs/header/footer remain full-width. Standalone forms and lifecycle/support/import action panels use the shared form-panel utility: theme border, 8px radius, surface and 16px/24px responsive padding. Assignment sections provide the frame for their nested form; popover/modal forms retain their existing outer frame. Manage Resident places the Status heading and badges in one wrapping row, above account actions.

All confirmation popups use ConfirmDialog: fixed viewport centring on mobile and desktop, bounded width, phone gutters and internal scrolling above 90dvh. Keep native modal focus/Escape behavior. This does not centre dropdowns or autocomplete lists, which remain by their controls.

The shared Pagination renders filtered Page X of Y · N results, accessible icon-only First/Previous/Next/Last, and a GET page-size form (10/25/50/100) with a custom width-constrained dropdown. The shared client component navigates immediately on selection, preserving filters and omitting the previous page; there is no apply button or separate record-range line. Votes, Residents, Manage Votes, Audit History, participation and completed PUBLIC named responses request validated numbered metadata. Residents and Manage Votes use specialized table-page routines for globally filtered ordered IDs. Manage Votes additionally returns only aggregate submitted/eligible counts for Active and Completed rows, using the frozen electorate denominator; its HTTP cursor projection remains unchanged. Audit uses get_audit_list_page when its text filters are active; the generic list service uses get_list_page for bounded cursor anchors. Counts and IDs/anchors remain caller-authorized. HTTP cursor envelopes and export semantics are unchanged. UI page values beyond the end clamp to the last page; empty sets show page 1 of 1. Filters/size changes restart at page 1; Residents remounts its page-scoped selection state on page/size changes. Missing count metadata fails explicitly, never produces a guessed total. Table regions are labelled and keyboard-focusable to contain overflow when larger pages include wider data. See pagination contracts for concurrency and access details.

Current export controls are ordinary download links: generation progress, in-progress deduplication and inline recoverable errors remain an acknowledged UX gap. Do not document those missing behaviors as implemented.

App Support Access (RWA-controlled read-only help)

For live in-app help, an enabled RWA Admin can turn App Support Access on or off from Settings. Setting the server-only APP_SUPPORT_EMAIL only makes the toggle available; it grants nothing by itself. When on, the guarded set_app_support_access routine creates (or re-enables) a single household-free, read-only rwa-readonly profile (profiles.is_app_support) for that address, so the developer signs in through the normal email OTP flow and sees the committee read scope but has no electorate row and cannot vote. A check constraint keeps the profile read-only, triggers block ordinary edits (APP_SUPPORT_MANAGED) and any household assignment (APP_SUPPORT_ACCOUNT), and both toggles are audited (APP_SUPPORT_ACCESS_ENABLED/APP_SUPPORT_ACCESS_DISABLED). The service layer (src/server/settings/app-support.ts) orders Auth and database steps fail-safe (unban before enable, suspend before ban). This is consented, revocable support access, never a hidden login or standing default administrator.

13. A safe workflow for your first code change

  1. Identify the exact requirement and relevant page/API/service/SQL contract.
  2. Read nearby tests and reuse established components/helpers before adding new logic.
  3. Write a focused regression or acceptance test. Reproduce the old failure when possible.
  4. Change shared validation first when input/output shapes change; update related server/database/UI surfaces together.
  5. Add a new migration if persistence/permissions need changing. Test fresh schema and upgrade/data preservation, not just an empty mock.
  6. Preserve privacy and atomicity. Never fix a display problem by altering counters manually or weakening an RLS policy.
  7. Exercise loading/empty/success/error paths and the relevant viewport/keyboard flow.
  8. Run focused tests, types and lint, then expand to the affected integration/browser/build checks.
  9. Update directly related documentation. Report actual evidence and remaining limits.
  10. Have a reviewer inspect permissions, historical data compatibility, rollback and production risk.

Example: adding a required draft field involves its shared Zod schema, editor, draft service/RPC, database constraints and preview/activation readiness, result/export snapshot if historically relevant, tests and contract docs. Changing only a text input is incomplete.
